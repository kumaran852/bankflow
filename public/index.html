Project at a glance

  • Problem — manual/spreadsheet banking records are slow to search, easy to duplicate and unsafe during money transfers.
  • Approach — one normalized relational database (3NF) holding branches, employees, customers, accounts and transactions.
  • Guarantee — deposit, withdrawal and transfer run inside ACID transactions with validation, row locking and rollback.
  • Audit — every balance change writes a row in transactions, so no money moves untraced.
  • Integrity — PRIMARY KEY, FOREIGN KEY, NOT NULL, UNIQUE and CHECK constraints plus a delete-guard trigger.
  • Programmability — stored procedures, a balance function, a cursor-based interest run and reusable views.
  • Performance — composite index on (account_no, txn_time) verified with a query plan.
  • Extras — MongoDB-style document CRUD and a B+ Tree simulation for the account index.

    Normalization
    up to 3NF
    
        
    
          
      
            
    • 1NF — every attribute is atomic and each table has a primary key; a customer's several accounts are separate rows in accounts, not a repeating group.
      • 
            
    • 2NF — every table has a single-column key, so no non-key attribute depends on part of a key.
      • 
          
    
          
      
            
    • 3NF — no non-key attribute depends on another non-key attribute. Branch details live only in branches; accounts keeps just the customer_id and branch_id references.
      • 
            
    • Design note — transactions.balance_after is a deliberate snapshot written in the same transaction as the balance update, so a statement can be printed without recomputing history.
      •

    Implementation note
    how the prototype maps onto the MySQL design of the report
    
        
      
          
    • Engine — the runnable prototype uses the SQL engine built into Node.js (SQLite dialect) so the demonstration needs no server installation. The MySQL 8.0 script remains the primary deliverable and is shown in full under SQL Source.
      • 
          
    • Stored programs — sp_deposit, sp_withdraw and sp_transfer run as server-side routines that wrap the same statements in BEGIN IMMEDIATE / COMMIT / ROLLBACK, in the same validation order and returning the identical status messages.
      • 
          
    • Row locking — MySQL locks the two account rows with SELECT … FOR UPDATE in ascending account-number order; the prototype takes the same order inside one exclusive write transaction, so two opposite transfers cannot interleave.
      • 
          
    • Trigger and constraints — PRIMARY KEY, FOREIGN KEY, NOT NULL, UNIQUE and CHECK constraints, the delete-guard trigger, both views and both indexes are real objects in the prototype database (see above).
      • 
          
    • Access control — CREATE USER / GRANT are MySQL specific, so the privilege matrix above records exactly what the MySQL script grants the teller.

    B+ Tree simulation
    
          Experiment 11
        
    
        
    
          Order 4 (at most 3 keys per node). Records live only in the linked leaves; internal nodes carry separator keys, which
          is why a date-range statement needs one descent plus a walk along the leaf chain.
